### Installed frontend evidence for legacy rollback

Read-only inspection of the installed app.asar found real `thread/rollback`
requests for legacy edit, fork trimming and retry, alongside a separate paginated
`thread/revert` path. These are call sites, not merely embedded schema strings:

- `.vite/build/main-BR_2NHW6.js`, SHA256
  `1f2b91cf92fc023fb2fa41e1c1d03698fa6e37354ecd07dd0cebd21337607b08`.
- `webview/assets/app-initial-8f0e46979798.js`, SHA256
  `627397c055589927c65d1ff9490e5956a38982cd22c9ab998570c09088ea1e63`.

Upstream removal of the API therefore cannot yet retire the fork's compatibility
route, even though historical rollback replay also has independent reasons to
survive. Version proximity alone did not settle this question.

A separate receiver/API review caught two integration defects before deployment:
the restored route did not enter upstream's listener/unload lifecycle, and sender
drop ambiguously meant both terminal completion and cancellation. It now uses
the existing subscription owner and a bounded PendingRollback context. Queued
response/error precedes explicit acknowledgement; listener loss returns an RPC
error instead of merely releasing admission. Focused public-RPC and handler/state
regressions cover resubscription, response ordering and cancellation.

## Data migration and downgrade boundary

New state migrations55–57 rename artifact storage to attachments, add nullable
creator identity columns, and trim synthetic Guardian projection text. Thread
history7 adds nullable item lifecycle timestamps; memoriesV1 migration2 adds
consolidation progress. The old fork accepts unfamiliar migration versions while
continuing to enforce checksums for known versions. Source inspection found no
old runtime SQL consumer of the renamed artifact table and named-column writes
for the additive fields. That supports a copied-database test; it does not by
itself prove every downgrade operation.

Read-only intake aggregates found242 Guardian-source rows with14,889,400
characters each in title and first-user-message projections. Migration57 clears
synthetic first messages, shortens automatically derived titles and preserves
different explicit titles/names. Canonical rollout history remains intact. The
projection burden is concrete; its share of UI latency remains unmeasured.

Source contact also found no changed digest projection for historical inline
images and function/custom outputs: the new ImageReference wrapper is flattened
and untagged, and the old metadata wire names/omissions remain. Four fixed,
synthetic historical-golden cases were added from the c196cb9 source contract,
with independently calculated hashes and a changed-payload rejection. These are
source-derived goldens, not captures from executing the old binary.

The first executing matrix caught a real historical-reference compatibility
gap: the merged checkpoint-local scan discarded preceding turn/settings records
for old reference checkpoints that lack `resume_metadata`. The repair keeps
native Paginated and complete new checkpoints bounded locally, while old
RefsV1/V2 recover the earlier completed-turn metadata baseline and only demanded
reference sources. Selection uses the canonical rollout generation rather than
the SQLite family projection. Paired old/new checkpoint tests protect this
distinction; making the failing expectation smaller would have hidden the loss.

The Windows probe now preserves per-database online backups and rehearses
candidate → previous → candidate startup in a separate home. It only lists DB
metadata and candidate attachments; it never resumes real source rollouts. Lazy
history stores not reached by this path need their focused tests rather than a
claim that startup tested them. Binary rollback does not undo projection cleanup.
